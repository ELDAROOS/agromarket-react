# АгроМаркет — React

Frontend подключён к собственному Express API: `http://localhost:3000/api`.
ФИО не указывается по пожеланию пользователя.

## Запуск

Нужен Node.js 22.22.2+, 24.15.0+ или 26+ (точные диапазоны — в `package.json`).

В первом терминале запустите отдельный backend, расположенный рядом:

```sh
cd ../agromarket-server
npm install
npm run db:local:start
npm run dev
```

Во втором терминале, в этой папке:

```sh
npm install
npm run dev
```

Откройте `http://localhost:5173`. Порт закреплён: если он занят, Vite сообщит об ошибке вместо смены порта, которая нарушила бы настройки CORS. json-server больше не используется.

## Что сделано

- Каталог загружает товары через `GET /api/products` с обработкой загрузки и ошибки.
- Существующий поиск по названиям работает в React без учёта регистра. Сервер также поддерживает независимые запросы `search`, `maxPrice`, `sort`.
- Форма отправляет `product_id`, `name`, `email`, `phone`, `quantity`, `date`, `comment` через `POST /api/orders` в JSON.
- Успех: alert с номером заявки и очистка формы. Ошибка API или недоступный сервер: alert, введённые данные сохраняются.
- Во время запроса кнопка отключена и показывает «Отправка…», повторная отправка блокируется.
- В форме можно выбрать товар: `product_id` сохраняется в PostgreSQL, название доступно через JOIN.
- Каталог загружает все страницы API по 100 товаров.
- Общий адрес API и авторизованные запросы вынесены в `src/api.js`.
- Добавлены регистрация, вход, выход, проверка `/auth/me`, смена пароля и автоматический выход при истёкшем или испорченном токене.
- Обычный пользователь видит только свои заявки; администратор видит панель всех заявок, меняет статус и управляет товарами.
- Оригинальные товары и оформление сохранены.

## Проверка вручную

1. Откройте каталог, в Network найдите `GET http://localhost:3000/api/products?limit=100&offset=0`: 200.
2. Заполните форму, укажите не менее 10 кг и отправьте. Появится «Заявка №… принята!».
3. Откройте `http://localhost:3000/api/orders`: заявка находится в списке.
4. В консоли браузера выполните:

```js
fetch('http://localhost:3000/api/orders', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Тест', email: 't@t.kz', quantity: 5 }),
}).then(async (response) => console.log(response.status, await response.json()));
```

Ожидается 400 и «Минимальный объём заказа — 10 кг».
Заявки хранятся в PostgreSQL и сохраняются после перезапуска backend и базы.
В этой копии база уже подготовлена; на другом компьютере настройте `.env` и выполните `npm run db:init` один раз по README backend.

## Лабораторная 7

Frontend подключён к JWT-аутентификации backend. Новый пользователь регистрируется с ролью `user`; форма товара и панель всех заявок видны только администратору. Токен хранится в `localStorage`, автоматически добавляется как `Authorization: Bearer ...`, а при ответе 401 сессия очищается. Реальная проверка доступа выполняется Express middleware, поэтому скрытие кнопок в React не является защитой.

Проверка сценария: зарегистрировать пользователя, обновить страницу, отправить заявку и открыть «Мои заявки»; войти администратором, добавить и удалить товар, изменить статус заявки. Локальный пароль администратора хранится в исключённом из Git файле `../agromarket-server/ADMIN_ACCESS.txt`.

## Лабораторная 7 — ответы для защиты

- Одинаковые пароли дают разные bcrypt-хэши: используется случайная соль; `compare` проверяет пароль, а cost 10 делает перебор дорогим.
- Поле `role` из регистрации игнорируется, поэтому тело с `role: admin` всё равно создаёт `user`; это защита от mass assignment.
- Регистрация возвращает 201 без `password_hash`; повторный email возвращает 409; короткий пароль — 400.
- JWT состоит из header, payload и signature. Header и payload можно прочитать, но изменение роли ломает подпись; при утечке `JWT_SECRET` злоумышленник сможет выпускать токены.
- 401 означает отсутствие или недействительность токена, 403 — корректный токен без нужной роли. `requireRole` выполняется после `requireAuth`; роль дополнительно читается из базы.
- Одинаковое сообщение для отсутствующего email и неверного пароля не раскрывает, какие адреса зарегистрированы.
- Токен в React хранится в localStorage и добавляется `apiFetch`; выход удаляет token и user. Недостаток localStorage — XSS может прочитать токен; в production предпочтительнее httpOnly cookie с CSRF-защитой.
- Прятать форму в React недостаточно: настоящий запрет находится в `requireAuth` и `requireRole('admin')` на сервере.
- OPTIONS — CORS preflight для POST/PUT/DELETE с JSON и Authorization; `cors()` отвечает до логгера и маршрутов.
- Ошибка JSON теперь 400, тело больше 10 КБ — 413, шестая неудачная попытка входа в 15-минутном окне — 429 с RateLimit/Retry-After.

## Переменные окружения

`JWT_SECRET` — случайная строка не менее 32 байт; `JWT_EXPIRES_IN` — например `2h`; `ADMIN_EMAIL` и `ADMIN_PASSWORD` задают первого администратора. Настоящие значения находятся только в `.env`; `.env.example` содержит шаблон. `npm run db:migrate` добавляет users к уже существующей базе без сброса товаров и заявок.

### E2E локально

Установите зависимости соседнего `../agromarket-server` и запустите его локальную PostgreSQL. Сам Express API вручную запускать не требуется.

```sh
npm --prefix ../agromarket-server ci
npm --prefix ../agromarket-server run db:local:start
npx playwright install chromium
npm run e2e
```

Playwright поднимает отдельные процессы: API на `http://127.0.0.1:3100` и Vite на `http://127.0.0.1:5174`. Эти порты должны быть свободны. В API используется тот же Express-код, что и в основном приложении.

`scripts/e2e-api.mjs` читает локальный DATABASE_URL из backend `.env`, создаёт случайную схему `lab12_e2e_*`, заполняет её товарами и временным администратором. Таблицы основного проекта не изменяются. При обычном завершении и сигналах SIGINT/SIGTERM временная схема удаляется. После принудительного SIGKILL очистка не гарантируется. Пароль администратора генерируется на каждый запуск и передаётся через окружение; JWT_SECRET также временный. Лимитер использует существующий серверный режим NODE_ENV=test, поэтому тесты не зависят от предыдущих попыток входа.

При необходимости создайте `.env.e2e` по комментариям в `.env.e2e.example`: `E2E_DATABASE_URL` позволяет выбрать другую **локальную** базу с правом CREATE SCHEMA, `E2E_FARMER_EMAIL` и `E2E_FARMER_PASSWORD` задают временную учётную запись. Конфигурация загружает эти переменные автоматически; настоящие секреты исключены из Git. Роль управления товарами в интерфейсе этого проекта — `admin`, поэтому сценарий фермера адаптирован под администратора.

Шесть сценариев: каталог из настоящего API; переход к товару и обновление страницы; регистрация, восстановление сессии и выход; неверный пароль; создание/удаление товара через UI; отклонение цены -500 браузером.

```sh
npm run e2e -- --list        # список сценариев без запуска API и браузера
npx playwright test --ui
npx playwright show-report
```

### Какие недоделки нашли и исправили

Каталог заменял пустой ответ сервера демонстрационными товарами. При ошибке API показывались те же товары, а текст ошибки не выводился. Теперь пустой ответ показывает «Товары не найдены», сетевой сбой/500 — видимое сообщение с role=alert; несуществующие товары не предлагаются к заказу.

Название карточки не было ссылкой, отсутствовала страница товара. Добавлен маршрут `/products/:id`, загрузка отдельного товара через API, состояния загрузки/404 и возврат в каталог. В форме товара min=0 расходился с серверным правилом положительной цены; теперь min=1 при целочисленном step=1. Связи label/input в формах уже присутствовали.

Первые запуски тестов также выявили неоднозначные запросы: текст загрузки встречается и в каталоге, и в option формы заказа; поле Email присутствует и в авторизации, и в заказе. Проверка загрузки уточнена по role=status, поля входа ищутся внутри конкретной формы.

### Почему MSW, а не vi.mock(fetch)

MSW перехватывает запросы на уровне сети: реальные apiFetch, формирование URL, заголовков и тела, чтение JSON и обработка статуса продолжают выполняться. Поэтому тест проверяет взаимодействие компонента с HTTP API. Подмена fetch потребовала бы вручную воспроизводить интерфейс Response и сильнее связала бы тесты с устройством реализации. Порядок listen → resetHandlers → close соответствует [документации MSW](https://mswjs.io/guides/integrations/node).

### Почему полные E2E нельзя запускать на продакшене, а smoke можно

Регистрация создаёт пользователя, сценарий администратора создаёт и удаляет товар. На рабочем сайте это изменит реальные данные и может задеть пользователей или лимиты авторизации. Smoke выполняет только чтение. Полный набор использует изолированную локальную схему; внешние адреса автоматически ограничены меткой @smoke.

### Что показал трейс упавшего E2E

После установки Chromium revision 1254 оба smoke-теста остановились при запуске браузера: `bootstrap_check_in ... Permission denied (1100)`. Системный Chrome также завершился до открытия страницы. Это ограничение среды выполнения; до page.goto и пользовательских шагов тесты не дошли. Поэтому снимка страницы приложения в трейсе нет. Учебный разбор намеренно сломанной проверки интерфейса ещё предстоит выполнить после успешного локального прогона.

Для демонстрации временно замените ожидаемое название в одном E2E-тесте, выполните его, откройте `npx playwright show-report` и вложение Trace. Найдите упавший expect, снимок страницы и ответы сети, затем верните ожидание. Конфигурация сохраняет trace и скриншот при ошибке (`retain-on-failure`, `only-on-failure`), поэтому повторный прогон для получения трейса не нужен. Возможности отчёта описаны в [Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer).

### Ошибка цены -500 — браузер или сервер

E2E-сценарий проверяет встроенную HTML-валидацию: у поля type=number, min=1; для -500 устанавливается validity.rangeUnderflow, появляется validationMessage и POST не отправляется. Этот сценарий подготовлен, но его выполнение в браузере ещё не подтверждено. Отдельный прошедший компонентный тест намеренно обходит браузерную валидацию через submit и проверяет ответ MSW 400 с details.price. Настоящая серверная схема Zod дополнительно проверяет positive(): HTML можно обойти прямым HTTP-запросом, поэтому серверная проверка обязательна.

### CI и оставшиеся действия для сдачи

`.github/workflows/ci.yml` запускает job `test` на pull request и push в main: npm ci → lint → test:run → build. Автозапуск локальных серверов E2E настроен через [webServer Playwright](https://playwright.dev/docs/test-webserver); в обязательный CI входят компонентные тесты и сборка.

1. Завершить локальный E2E-прогон и разобрать трейс намеренно упавшей проверки; обновить таблицу фактическим временем.
2. Опубликовать изменения ветки `test/frontend`, открыть PR и получить ревью напарника. Для отдельного PR документации использовать `docs/lab12` по заданию.
3. В GitHub Settings → Rules → Rulesets для main включить Require status checks to pass и выбрать job `test`. Локальное изменение workflow само по себе не включает защиту ветки.
4. Проверить зелёный GitHub Actions и сохранить скриншот. В отдельной ветке временно сломать тест, открыть PR, убедиться в блокировке merge и закрыть его без слияния.
5. После публикации обновлённого клиента выполнить два production smoke-теста, внести время и приложить ссылки на PR.

Автоматическая проверка разрешений отклонила повышение доступа, так как sandbox_approval отключён в настройках сессии.

Для повторного запуска в обычном терминале:

```sh
npm --prefix ../agromarket-server run db:local:start
npm run e2e
BASE_URL=https://agromarket-eldaroos.vercel.app npm run e2e:smoke
```

При желании использовать установленный Google Chrome вместо кеша Chromium задайте `E2E_BROWSER_CHANNEL=chrome`. Последнюю команду production smoke следует выполнять после публикации текущих изменений клиента.

## Лабораторная 13 — розничные заказы

- Товар можно добавить в корзину из каталога и со страницы товара. Остаток ограничивает количество, а при нулевом остатке кнопка недоступна.
- Корзина хранится в React Context и `localStorage`. Страница `/cart` показывает количество, предварительный итог и форму адреса после входа. При ответе API 409 корзина сохраняется и показывает доступное количество.
- На странице `/orders` можно посмотреть свои заказы и отменить новый. Фермер видит заказы на свои товары на `/orders/incoming`. Остаток задаётся при добавлении или редактировании товара.
- API должен быть развёрнут после миграции `013_orders.sql`. Запуск клиентского приложения на локальном API — `npm run dev`.

```sh
npm run test:run
npm run lint
npm run build
npm run e2e
```

Для Playwright нужны соседний репозиторий `agromarket-server` и локальная PostgreSQL. Тесты автоматически поднимают API во временной схеме. Сценарий `e2e/order.spec.js` оформляет заказ и отменяет его, проверяя остаток до и после. При заданном `BASE_URL` выполняются только сценарии чтения с меткой `@smoke`, включая открытие корзины.
