Frontend подключён к собственному Express API: `http://localhost:3000/api`.
ФИО не указывается по пожеланию пользователя.

## Запуск

Нужен Node.js 22.12+.

В первом терминале запустите отдельный backend, расположенный рядом:

```sh
cd ../agromarket-server
npm install
npm run db:local:start
npm run dev
```

Во втором терминале, в этой папке:

```sh
npm install
npm run dev
```

Откройте `http://localhost:5173`. Порт закреплён: если он занят, Vite сообщит об ошибке вместо смены порта, которая нарушила бы настройки CORS. json-server больше не используется.

## Что сделано

- Каталог загружает товары через `GET /api/products` с обработкой загрузки и ошибки.
- Существующий поиск по названиям работает в React без учёта регистра. Сервер также поддерживает независимые запросы `search`, `maxPrice`, `sort`.
- Форма отправляет `product_id`, `name`, `email`, `phone`, `quantity`, `date`, `comment` через `POST /api/orders` в JSON.
- Успех: alert с номером заявки и очистка формы. Ошибка API или недоступный сервер: alert, введённые данные сохраняются.
- Во время запроса кнопка отключена и показывает «Отправка…», повторная отправка блокируется.
- В форме можно выбрать товар: `product_id` сохраняется в PostgreSQL, название доступно через JOIN.
- Каталог загружает все страницы API по 100 товаров.
- Общий адрес API и авторизованные запросы вынесены в `src/api.js`.
- Добавлены регистрация, вход, выход, проверка `/auth/me`, смена пароля и автоматический выход при истёкшем или испорченном токене.
- Обычный пользователь видит только свои заявки; администратор видит панель всех заявок, меняет статус и управляет товарами.
- Оригинальные товары и оформление сохранены.

## Проверка вручную

1. Откройте каталог, в Network найдите `GET http://localhost:3000/api/products?limit=100&offset=0`: 200.
2. Заполните форму, укажите не менее 10 кг и отправьте. Появится «Заявка №… принята!».
3. Откройте `http://localhost:3000/api/orders`: заявка находится в списке.
4. В консоли браузера выполните:

```js
fetch('http://localhost:3000/api/orders', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Тест', email: 't@t.kz', quantity: 5 }),
}).then(async (response) => console.log(response.status, await response.json()));
```

Ожидается 400 и «Минимальный объём заказа — 10 кг».
Заявки хранятся в PostgreSQL и сохраняются после перезапуска backend и базы.
В этой копии база уже подготовлена; на другом компьютере настройте `.env` и выполните `npm run db:init` один раз по README backend.

## Лабораторная 7

Frontend подключён к JWT-аутентификации backend. Новый пользователь регистрируется с ролью `user`; форма товара и панель всех заявок видны только администратору. Токен хранится в `localStorage`, автоматически добавляется как `Authorization: Bearer ...`, а при ответе 401 сессия очищается. Реальная проверка доступа выполняется Express middleware, поэтому скрытие кнопок в React не является защитой.

Проверка сценария: зарегистрировать пользователя, обновить страницу, отправить заявку и открыть «Мои заявки»; войти администратором, добавить и удалить товар, изменить статус заявки. Локальный пароль администратора хранится в исключённом из Git файле `../agromarket-server/ADMIN_ACCESS.txt`.

## Лабораторная 7 — ответы для защиты

- Одинаковые пароли дают разные bcrypt-хэши: используется случайная соль; `compare` проверяет пароль, а cost 10 делает перебор дорогим.
- Поле `role` из регистрации игнорируется, поэтому тело с `role: admin` всё равно создаёт `user`; это защита от mass assignment.
- Регистрация возвращает 201 без `password_hash`; повторный email возвращает 409; короткий пароль — 400.
- JWT состоит из header, payload и signature. Header и payload можно прочитать, но изменение роли ломает подпись; при утечке `JWT_SECRET` злоумышленник сможет выпускать токены.
- 401 означает отсутствие или недействительность токена, 403 — корректный токен без нужной роли. `requireRole` выполняется после `requireAuth`; роль дополнительно читается из базы.
- Одинаковое сообщение для отсутствующего email и неверного пароля не раскрывает, какие адреса зарегистрированы.
- Токен в React хранится в localStorage и добавляется `apiFetch`; выход удаляет token и user. Недостаток localStorage — XSS может прочитать токен; в production предпочтительнее httpOnly cookie с CSRF-защитой.
- Прятать форму в React недостаточно: настоящий запрет находится в `requireAuth` и `requireRole('admin')` на сервере.
- OPTIONS — CORS preflight для POST/PUT/DELETE с JSON и Authorization; `cors()` отвечает до логгера и маршрутов.
- Ошибка JSON теперь 400, тело больше 10 КБ — 413, шестая неудачная попытка входа в 15-минутном окне — 429 с RateLimit/Retry-After.

## Переменные окружения

`JWT_SECRET` — случайная строка не менее 32 байт; `JWT_EXPIRES_IN` — например `2h`; `ADMIN_EMAIL` и `ADMIN_PASSWORD` задают первого администратора. Настоящие значения находятся только в `.env`; `.env.example` содержит шаблон. `npm run db:migrate` добавляет users к уже существующей базе без сброса товаров и заявок.

## Тестирование

Лабораторная работа №10: Vitest + React Testing Library + user-event + jsdom,
моки настоящего `fetch` через `vi.spyOn`, браузерные сценарии Playwright Chromium.
Нужен Node.js 22.13+ (в CI используется актуальный Node 22).

```sh
npm ci
npm test                 # 21 компонентный тест, настоящий API не нужен
npm run test:watch       # перезапуск при изменениях
npm run coverage        # текстовый отчёт и coverage/index.html
npx playwright install chromium
npm run e2e             # автоматически запускает Vite; Express и PostgreSQL нужны отдельно
npm run e2e:prod         # https://agromarket-eldaroos.vercel.app
npx playwright show-report
```

`E2E_BASE_URL` переопределяет адрес production в `npm run e2e:prod`.
Если она установлена, Playwright не запускает локальный Vite.
В CI `PRODUCTION_URL` передаётся в `E2E_BASE_URL`, пустое значение останавливает workflow.
Vitest запускает только `src/**/*.test.{js,jsx}` и не подхватывает `e2e/*.spec.js`.
После каждого компонентного теста очищаются DOM, моки, localStorage и URL.
Незамоканные запросы отклоняются, поэтому тесты не обращаются к рабочему серверу.

### Локальный backend на этом компьютере

Порт 5432 занят другой PostgreSQL. Учебный кластер проекта запускается на 5433;
чужой кластер и `.env` не изменяются. В каталоге `../agromarket-server`:

```sh
/opt/homebrew/opt/postgresql@16/bin/pg_ctl -D .postgres -l .postgres/server.log -o '-p 5433' -w start
node --input-type=module -e "import dotenv from 'dotenv'; dotenv.config({quiet:true}); const u=new URL(process.env.DATABASE_URL); u.port='5433'; process.env.DATABASE_URL=u.href; await import('./server.js');"
```

Первую команду выполнять только при остановленном учебном кластере. API слушает 3000.
В другом терминале, в каталоге frontend: `npm run e2e`.
Остановка API — Ctrl+C, учебной БД — `npm run db:local:stop` из backend.
На другом компьютере сначала настроить базу по README backend; автоматический сброс данных не нужен.

### E2E и CI

Четыре сценария в `e2e/buyer.spec.js` проверяют:

1. Ответ настоящего `/api/products` со статусом 200 и отображение товара из этого ответа.
2. Ответ 200 и форму входа при прямом открытии `/login`.
3. Регистрацию уникального `e2e+<UUID>@agromarket.test`, выход, повторный вход,
   добавление в корзину, заявку на 10 кг, номер заявки в истории и сохранение после F5.
4. Сообщение об отсутствии доступа на `/admin` и отсутствие административных действий у гостя.

Моков и перехвата API в E2E нет. Оптовая заявка API содержит один товар и минимум 10 кг,
а розничная корзина считает единицы; сценарий явно выбирает тот же товар в форме заявки.
Тест не удаляет данные и не использует права администратора. Комментарий заявки:
«Учебная E2E-заявка. Не обрабатывать.»

Workflow `CI` выполняет `npm ci → lint → test → build` для PR и push в main.
Job `build` обязателен в защите main, требуется актуальная база ветки и одно одобрение ревью;
правило распространяется и на администратора. `PRODUCTION_URL` настроена на адрес Vercel.
Workflow `E2E (production)` запускается ежедневно в 04:00 UTC (09:00 Алматы/Астана)
и вручную, хранит HTML-отчёт и `test-results` семь дней.

### Ответы для защиты

1. **Пирамида:** основание — быстрые компонентные Vitest/RTL и unit-тесты сервера;
   середина — Supertest + PostgreSQL из ЛР8; вершина — четыре Playwright-сценария.
   Чем больше реальных зависимостей, тем медленнее и нестабильнее запуск.
2. **jsdom:** реализация DOM в Node.js, а не настоящий движок браузера.
   Подходит для рендера React и событий; не доказывает правильность CSS-layout,
   реального изображения, CORS браузера и взаимодействия приложения с production.
3. **Роли и label:** соответствуют доступным именам, которыми пользуется человек и
   экранный диктор; CSS-классы могут меняться при сохранении поведения.
4. **getBy/queryBy/findBy:** getBy немедленно требует элемент; queryBy возвращает null
   при отсутствии; findBy асинхронно ждёт появления. Неоднозначные совпадения требуют
   уточнения имени или `within`.
5. **Мок:** управляемая подмена зависимости. Fetch-мок делает проверку быстрой и воспроизводимой;
   неверный формат фикстуры может скрыть несовместимость с API, поэтому E2E использует настоящий сервер.
6. **Состояния экрана:** загрузка, данные и ошибка; дополнительно нужен пустой результат.
   Проверка только успешной загрузки не обнаружит пустой экран при отказе сервера.
7. **vi.fn:** функция-шпион. `toHaveBeenCalledWith` проверяет аргументы,
   `not.toHaveBeenCalled` — отсутствие вызова, `toHaveBeenCalledTimes` — число вызовов.
8. **E2E / smoke / Supertest:** E2E проходит пользовательский путь в браузере;
   smoke быстро проверяет доступность после деплоя; Supertest проверяет HTTP-маршруты
   Express и их интеграцию с БД без React и браузера.
9. **Окружение E2E:** production проверяет уже опубликованную версию; preview/staging
   позволяет проверить кандидат до публикации. Тестовые данные должны быть изолированы.
10. **Удаление в production:** ошибка сценария с широкими правами может затронуть реальные данные.
    Покупательский тест имеет обычную роль user и только создаёт свои записи.
11. **Покрытие:** показывает выполненные строки, ветви, функции и выражения.
    Даже 100% не доказывает полноту утверждений, входных случаев и правильность требований.
12. **Найденный дефект:** вместо ошибки API и пустого ответа отображались запасные товары.
    Теперь это проверяют отдельные тесты; фиктивные ID не попадают в выбор товара для заявки.
